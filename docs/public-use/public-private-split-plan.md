# 仓库公开 / 私有拆分方案

更新时间：2026-04-10

## 先说结论

“不要把真实工作内容变成公开资料”这个担心是成立的。

当前仓库里已经不只是一个通用工具壳，还混着不少接近真实业务的内容：

- 原始需求邮件
- 真实合同模板与样本
- 真实业务命名习惯
- 真实站点与查询入口
- 带明显业务痕迹的 PRD / 技术方案 / 示例文件

如果继续把这些内容和桌面应用一起公开，别人拿到的就不只是“一个工具”，而是越来越接近你的真实工作做法与积累。

更稳的路线是：

1. 公开 `工具层`
2. 私有 `业务层`
3. 通过 `公开 release + 私密业务包` 的方式继续让内部人方便使用

## 哪些内容更像“工作内容”

### 建议优先转私有

- `our_requirements/**`
- 真实合同模板
- 真实站点配置
- 偏内部的 PRD / 技术方案
- 带真实业务命名的示例 Word / Excel / JSON

### 可以保留，但必须脱敏后再公开

- 演示模板
- 演示工作簿
- 演示帮助页截图
- 示例配置文件

脱敏的目标不是“把文件名改一下就完事”，而是要把：

- 船名
- 公司名
- 合同号规则
- 银行信息
- 客户痕迹
- 真实站点地址和真实查询条件

都替换成演示内容。

### 适合继续公开

- `desktop_app/`
- 自动更新逻辑
- 通用 GUI
- 通用 Excel / Word / 同步引擎
- 帮助中心框架
- 打包和更新基础设施

这些更体现“你做工具的能力”，而不是“你真实工作的底牌”。

## 最适合当前阶段的拆分方式

### 公开部分

保留在公开仓库和公开 release 里：

- 桌面应用本体
- 通用自动化能力
- 帮助中心框架
- 脱敏 demo
- 更新机制

### 私有部分

通过 `.amspack` 私下分发给内部人：

- 真实模板
- 真实模板映射规则
- 真实站点配置
- 私密帮助页

## 别人怎么用“公 + 私”版本

### 外部用户

1. 直接下载公开 release
2. 使用公开 demo 和公开功能
3. 如果要用于自己的业务，按公开文档替换成自己的模板和配置

### 内部用户

1. 下载同一个公开 release
2. 私下拿到 `.amspack`
3. 在应用设置页导入私密包并输入密码
4. 应用切换到“已解锁完整业务模式”

也就是说：

- 程序公开分发
- 真实业务内容私下分发
- 普通用户和内部用户最终都在同一个应用里工作

## 为什么不推荐“只加一个登录框”

因为如果私密文件已经跟着公开安装包一起发出去了，那么登录框只是在挡界面，并不能挡文件本身。

要防路人，正确方式一定是：

- 公开包里不带私密内容
- 私密内容单独加密
- 通过密码解锁私密包

## 当前推荐动作

1. 继续保留公开桌面版 release
2. 把真实业务内容逐步挪出公开仓库
3. 用私密包承接真实模板和真实配置
4. 以后新功能默认先按“公版可演示、私版承载真实内容”来设计

## 一句话总结

公开版负责让别人看到并用到你的产品能力；私密包负责装着你真正的业务 know-how。
