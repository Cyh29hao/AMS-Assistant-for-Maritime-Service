FUNCTIONS

AMS 不是泛用聊天页，而是三类明确业务动作。

每个模块都围绕一个结果展开：要么导出合同，要么回填表格，要么生成报表。

Module A

合同中心

读取业务表格，自动判断模板，补齐关键字段，输出结构完整的双语航次合同。

  • 适合优先做 MVP
  • 输入输出最明确
  • 不依赖网页登录

Module B

通关查询

登录目标网站查询提单状态，如已放行则自动回填业务表中的备货、PCS 和 MT。

  • 适合后续接定时任务
  • 对登录稳定性要求高
  • 失败日志必须清楚

Module C

船期汇总

读取 LINE UP 船名，查询外部结果后生成“港口 x 区域”的矩阵型船期表。

  • 适合第二阶段实现
  • 已有真实 Excel 样本
  • 输出形式容易标准化

DEPLOYMENT

给不同人准备不同的部署方式。

同一个 AMS 项目，不一定只有一种交付方法。入口页要轻，真正的自动化工具要稳。

Option 1

直接访问在线入口页

最轻量的方式。适合先把 AMS 的功能、边界和后续入口统一起来，不需要任何安装。

  • 适合所有人访问
  • 适合作为项目首页
  • 适合发给家人和同事浏览
Option 2

自己部署 GitHub Pages

适合希望快速复制一个相同入口页的人。只要会用 GitHub，就能几分钟部署出来。

git init
git branch -M main
git add .
git commit -m "Deploy AMS site"
git remote add origin YOUR_REPO_URL
git push -u origin main
Option 3

后续接本地网页工具

真正涉及 Word、Excel、网页登录自动化的能力，建议用本地运行方式接入，这样更稳也更安全。

  • 业务文件不需要上传公网
  • 账号和日志留在本机
  • 更适合重复日常操作

APPROACH

为什么首页能放在 GitHub Pages，但核心能力放在本地运行。

GitHub Pages 适合做什么

  • 项目首页与功能介绍
  • 面向同事的操作说明
  • 后续的工具下载入口
  • 轻量级前端展示页面

为什么不把全部自动化都放到纯网页里

  • Word 合同模板处理不适合纯前端长期维护
  • 网页登录查询涉及稳定性、跨域和账号安全
  • Excel 回填与定时任务更适合本地服务执行
  • 业务数据本地保存，对家人和同事更安心

FAQ

先把最容易误解的地方说清楚。

这个页面本身能直接出合同吗？

还不能。它现在是入口页和说明页。真正的合同生成、网页登录查询和 Excel 回填，会接到后续本地网页工具里。

妈妈和同事需要懂 GitHub 吗？

不需要。理想状态下，他们只需要打开你发给他们的页面链接，再进入后续本地工具即可。

为什么不直接做成纯在线系统？

因为业务里涉及 Word、Excel、网页登录和敏感数据，纯在线静态页不够稳，也不够适合长期复用。
