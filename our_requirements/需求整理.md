## 2. 总体结论

这 3 条需求都属于“航运业务自动化”方向，但和当前仓库里的“航运邮件助手”不是同一条主线。

当前项目主线是：

- 从邮箱抓邮件
- 抽取邮件中的船舶事件
- 入库后做查询

而这次 3 条新需求主线是：

- 根据业务表格自动生成合同
- 自动登录外部网站查询通关状态并回填表格
- 自动查询船期并汇总成报表

两者的共同点主要只有：

- 都是航运场景
- 都可能需要一个本地 Web 界面
- 都可能需要 SQLite / 定时任务 / 文件处理

但核心能力已经明显不同：

- 当前项目偏“邮件抽取 + 查询”
- 新需求偏“文档生成 + 网页自动化 + Excel 回填”

如果后续重点是这 3 条需求，建议按新方向重新规划，而不是把现有项目硬改过去。

## 3. 需求 1：系统出合同

### 3.1 需求目标

做一个小程序或系统，从业务表格中抓取指定行，自动选择合同模板，自动填写模板中的可变内容，输出 Word 合同。

### 3.2 输入

- 一份业务表格中的若干行数据
- 合同模板

### 3.3 输出

- 一份已经填充完成的 `.docx` 合同

### 3.4 已提供的样本

模板样本：

- `货代 境内样本.docx`
- `物流 境内样本.docx`
- `ASTAR 境外样本.docx`
- `RTA 境外样本.docx`

成品样本：

- `250204-MU CHUANG 362.docx`
- `260305-DONG PHU.docx`

### 3.5 我理解到的业务逻辑

- 系统需要先判断应该套用哪一份合同模板
- 模板中红色部分是待填字段
- 数据来源是表格中的一票或多票货物信息
- 生成的不是简单标题，而是整份双语航次合同

### 3.6 从样本中能看出的主要字段

- 合同编号
- 日期
- 船名
- 租家名称
- 船东名称
- 货物总量
- 货描
- 多条装港/卸港/货量/货名明细
- 装港
- 卸港
- laycan
- 装卸条款
- 滞期费/速遣费
- 运费及条款
- 银行信息

### 3.7 技术本质

这是一个“基于 Word 模板的合同生成器”，核心不是邮件，也不是聊天查询。

### 3.8 当前不确定项

- 模板选择规则是什么
- 表格的真实输入格式是什么
- 红字字段清单是否固定
- 多条货物明细如何映射到模板中的多行段落
- 合同编号生成规则是否固定

## 4. 需求 2：自动查通关状态并填充表格

### 4.1 需求目标

每天 17:00 自动登录 `https://dp.eptrade.cn/#/`，查询未通关提单号的状态。如果已放行，则自动修改表格中的备货状态，并抓取件数和毛重回填。

### 4.2 输入

- 一张业务表，表内至少包含：
  - 提单号
  - 当前备货状态
  - 其他业务字段

### 4.3 输出

- 更新后的业务表

### 4.4 业务动作

- 找出“未通关”的提单号
- 登录目标网站
- 逐票查询
- 判断状态是否为“已放行”
- 若是，则更新：
  - 备货状态 = 已通关
  - PCS
  - MT

### 4.5 技术本质

这是一个“定时网页自动化 + 表格回填”的 RPA 类需求。

### 4.6 主要风险

- 网站是否有验证码
- 登录是否稳定
- 页面是否容易改版
- 回填目标是 Excel 还是在线表格，目前不明确
- 提单号一票多结果时如何处理，目前不明确

## 5. 需求 3：生成船期表

### 5.1 需求目标

读取 `LINE UP` 文件中的船名，逐条去 `https://dp.eptrade.cn/#/template/pss014` 查询，再根据查询结果，把船名填入按港口和区域整理的船期表。

### 5.2 输入

- `SHA LINEUP 0309.xlsx`
- 船名列表

### 5.3 输出

- 一张整理好的船期表
- 形式看起来像“港口 x 区域”的矩阵

### 5.4 样本特征

Excel 中已有如下字段：

- 预靠码头
- 中文船名
- 英文船名
- 航次
- 船长
- 状态
- 计划抵锚地时间
- 靠泊/离泊时间
- 船代

邮件中的示例输出则是：

- 行：目的港
- 列：九区 / 十区 / 罗泾
- 单元格：填查询命中的船名和业务简称

### 5.5 技术本质

这是一个“Excel 读入 + 网站查询 + 结果聚合报表”的自动化工具。

### 5.6 当前不确定项

- 查询结果中哪一个字段决定落入“九区 / 十区 / 罗泾”
- 一个港口命中多条船时如何展示
- 输出是继续写回 Excel，还是生成新表
- 船名匹配是按中文名、英文名，还是模糊匹配

## 6. 这 3 条需求的共性

如果把这三条需求当成一个新项目，它们共享的能力会是：

- 读取 Excel / 表格数据
- 定时执行任务
- 登录并操作外部网站
- 生成业务文档或业务报表
- 保存处理结果和日志

更像一个“航运业务自动化工作台”，而不是“邮件助手”。

## 7. 和当前项目的一致性判断

## 7.1 一致的部分

- 行业背景一致，都是航运/货代业务
- 可以继续沿用 Python 技术栈
- FastAPI、本地网页、SQLite 这些基础设施仍然有复用价值

## 7.2 不一致的部分

- 当前项目的核心入口是邮箱和邮件正文
- 新需求的核心入口是 Excel、业务表格、外部网站
- 当前项目的核心输出是查询结果
- 新需求的核心输出是合同、回填表、船期报表
- 当前项目的抽取逻辑主要是文本规则
- 新需求的重点是模板映射、浏览器自动化、Office 文件写入

## 7.3 结论

从“业务方向”看，它们相关。

从“代码主线”看，它们不太一致，而且差异不小。

如果你接下来真正要做的是这 3 条需求，那么：

- 不建议继续把当前仓库当成主实现基础
- 更建议把当前仓库视为一个旧方向的 MVP
- 新开一个线程，从需求重新拆解、重新定义 MVP，会更顺

## 8. 我的建议

### 方案 A：新开线程，从零规划

适合情况：

- 你后面重点要做的就是这 3 条新需求
- 你不想被当前“邮件助手”的结构牵着走

建议做法：

- 重新定义项目目标
- 先只做 1 条最有价值的需求作为新 MVP
- 把“网页自动化、Excel、Word 模板”作为一等公民设计

这是我更推荐的路径。

### 方案 B：继续在当前仓库上迭代

适合情况：

- 你只是想保留这个仓库，慢慢演化
- 你能接受目录和代码含义逐渐偏离“邮件助手”

风险：

- 后面项目会越来越像“什么都做一点”的工具箱
- 架构会变乱
- 不利于你重新建立清晰记忆

## 9. 如果重新开始，建议的优先级

我建议先做需求 1，再看需求 3，最后再评估需求 2。

理由：

- 需求 1 的输入输出最清晰
- 需求 1 不一定依赖网页登录
- 需求 1 最容易做出一个可见成果
- 需求 2 和需求 3 都依赖外部网站自动化，风险更高

建议顺序：

1. 先把需求 1 做成“表格行 -> Word 合同”
2. 再做需求 3 的“船名 -> 查询 -> 报表”
3. 最后做需求 2 的“定时查询通关状态 -> 回填”
