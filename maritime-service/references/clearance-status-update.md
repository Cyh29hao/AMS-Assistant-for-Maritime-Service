# req2 自动查通关工作流

这份文档描述的是 `req2` 的业务目标和当前实现边界。

## 业务目标

`req2` 的目标是：

1. 找出业务表中还没有通关的提单
2. 去站点查询它们的通关状态
3. 如果已经放行，就把业务表中的 `备货` 改为 `已通关`
4. 同时回填 `PCS` 和 `MT`
5. 保留一份可追溯的执行报告

## 当前已落地的部分

当前这版已经可以稳定做这些事：

1. 生成 req2 专用 Excel 模板
2. 读取业务表和查询结果表
3. 判断哪些提单需要更新
4. 把命中的已放行结果回填到业务表
5. 输出更新后的 Excel
6. 输出 JSON 报告和文本报告
7. 对示例结果做自动自检

## 当前没有直接硬连的网站部分

当前这版没有默认硬连 `dp.eptrade.cn` 真实登录。

这是故意的，不是漏做。原因是：

1. 真实网页登录稳定性还没现场验证
2. 是否有验证码还没实测确认
3. 页面查询接口和字段名还没固化
4. 直接写死网页登录比 Excel 回填本身风险更高

所以现在的策略是：

1. 先把“表格读取 -> 规则判断 -> 回填 -> 报告”做扎实
2. 再把“站点查询”接成可插拔的一层

## 当前 Excel 结构

req2 模板里有 4 个工作表：

1. `说明`
2. `业务表`
3. `查询结果`
4. `执行报告`

### 业务表

这是操作员真正维护的业务记录。

至少要有这些列：

1. `备货`
2. `B/L NO.`
3. `PCS`
4. `MT`

### 查询结果

这是站点查询结果落地的地方。

目前支持这几列：

1. `B/L NO.`
2. `网站通关状态`
3. `是否已放行`
4. `PCS`
5. `MT`
6. `CBM`
7. `FRT TON`
8. `查询时间`
9. `原始备注`

## 更新规则

脚本的处理逻辑是：

1. 只处理 `备货` 不是 `已通关 / 已放行` 的行
2. 如果 `B/L NO.` 为空，则跳过
3. 如果查询结果里找不到这票提单，记为“未命中”
4. 如果查询结果显示已放行，就把 `备货` 改成 `已通关`
5. 如果查询结果里 `PCS / MT` 有值，就同步回填
6. 如果查询结果显示还没放行，就不改业务表状态

## 未来接真站点时的建议

推荐拆成两层：

1. `查询层`
   负责登录站点、查询提单、拿到原始结果
2. `回填层`
   负责把结果写回 Excel，并给出审计报告

这样就算网页登录变化，`回填层` 也不用推倒重来。

## 推荐下一步

如果你要继续把 req2 推到接近生产，建议按这个顺序：

1. 先拿一个真实业务 Excel 跑这版回填流程
2. 再拿一组真实查询结果人工填进 `查询结果`
3. 确认业务规则没问题后，再开发真实网页登录抓取
4. 最后再接定时任务
