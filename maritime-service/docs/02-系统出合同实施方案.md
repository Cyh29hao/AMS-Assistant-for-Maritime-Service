# 系统出合同实施方案

这份文档讲的是“它为什么这么做”。

如果你不是开发者，也可以把它当成“项目说明书”来看。

## 1. 当前已经做成什么了

当前已经做成的是：

- 一个可运行的 Word 合同生成主流程
- 支持 4 种模板类型
- 支持 JSON 输入
- 支持 Excel 输入
- 支持一键生成示例
- 支持一键自检

也就是说，它已经不是一个只有想法的空架子，而是一个能真实产出 `.docx` 的 workflow。

## 2. 为什么现在先把 req1 做深

因为 req1 的不确定性最少：

- 输入输出清晰
- 不依赖第三方网站登录
- 结果可见
- 最容易马上替代重复劳动

对于自动化项目来说，先做“最清晰、最容易交付成果”的流程，是最稳的推进方法。

## 3. 架构上怎么理解

这条 workflow 可以拆成 5 层：

1. 输入层
2. 校验层
3. 模板选择层
4. Word 写入层
5. 输出与审阅层

### 输入层

支持两种输入：

- JSON
- Excel 工作簿

这样做的原因是：

- 给系统/agent 集成时，JSON 最稳
- 给人直接操作时，Excel 最方便

### 校验层

程序会先检查：

- 模板类型对不对
- 日期格式对不对
- 货物明细有没有缺关键字段
- 核心头信息有没有缺失

这样可以在“生成之前”就把明显错误拦住。

### 模板选择层

核心配置文件是：

- `scripts/contract_template_registry.json`

它决定：

- 哪个模板文件对应哪个 `template_key`
- 每个字段写入 Word 的哪一段
- 哪些模板有货物表格
- 银行信息和签字表在什么位置

### Word 写入层

核心脚本是：

- `scripts/contract_workflow.py`

它做的主要事情：

1. 读入输入数据
2. 生成派生字段
3. 打开 `.docx` 模板
4. 按段落坐标写入内容
5. 对境内模板重建货物明细表
6. 输出新的 `.docx`

### 输出与审阅层

输出不仅有 Word，还会有 JSON 摘要。

这样做的好处是：

- 方便排错
- 方便留痕
- 以后方便接审批流

## 4. 为什么不用“完全智能猜字段”

因为合同这种东西，一旦猜错，代价比普通文本高很多。

我这里故意做成：

- 关键句子由你明确填写
- 程序负责稳定地写入模板

而不是：

- 让程序自动瞎猜港口句子、费用句子、法律条款句子

这不是保守，而是对业务负责。

## 5. 为什么不是占位符模板

理想状态当然是：

- 模板里全是 `{{vessel_name}}`、`{{laycan}}` 这种占位符

但你给到的现有材料是：

- 真实 Word 模板
- 固定视觉排版
- 红字位置可变

所以第一阶段我采用的是：

- “模板坐标写入法”

也就是：

- 预先记录每种模板的关键段落号
- 把相应字段写到对应段落

优点是：

- 不要求业务方重做模板
- 能立刻利用现有文档
- 落地更快

缺点是：

- 如果模板结构以后被大改，坐标就要重新校正

## 6. 现在最适合的真实工作流

我建议业务上先这样用：

1. 业务人员准备一份 Excel
2. 填头信息和货物明细
3. 生成 Word 合同
4. 人工快速检查
5. 发给客户或内部审阅

这是“半自动但非常实用”的方案。

## 7. 下一阶段如何继续增强

### 增强 1：真实业务表直接导入

现在的 Excel 是“生成器专用模板”。

下一步可以做：

- 从你们真实业务表里直接抓行
- 自动转成生成器输入

这样就更接近你邮件里说的“抓取我表格中的某几行内容”。

### 增强 2：模板字段可视化维护

现在模板坐标在 JSON 里维护。

下一步可以做成：

- 一份更友好的配置表
- 或者专门的模板校准脚本

### 增强 3：审批和归档

后面可以补：

- 生成后自动放入“待审核”
- 记录谁生成、何时生成、用的哪份数据
- 保存合同版本历史

## 8. 当前这套交付更适合谁

最适合：

- 需要快速减少重复出合同劳动的人
- 需要把“出合同”从口头流程变成可复用流程的人
- 想为以后更大自动化做地基的人
