# req2 和 req3 后续落地方案

这份文档是为了避免你以后忘了：现在虽然重点先做了 req1，但 req2 / req3 并没有被丢掉。

## 1. req2 是什么

req2 的目标是：

- 每天固定时间登录外部网站
- 查询未通关提单号
- 如果已放行，就自动回填表格

## 2. req3 是什么

req3 的目标是：

- 读 LINE UP 文件
- 拿船名去外部网站查询
- 按港口和区域生成船期表

## 3. 为什么这两个现在没直接做完

不是做不了，而是现在最不确定的点都在外部系统：

- 网站登录是否稳定
- 是否有验证码
- 页面 DOM 是否经常改
- 查询结果哪些字段才是真正业务判定字段
- 最终回填目标是什么格式

对于自动化项目来说，凡是依赖外部网页的，风险都比本地 Word 生成高很多。

## 4. req2 的推荐实施步骤

### 第一步

先做登录可行性验证。

要确认：

- 是否必须人工验证码
- 登录 cookie 能否复用
- 查询接口是不是页面里真实存在的 API

### 第二步

做一个只读版。

只做：

- 读表
- 查状态
- 输出报告

先不要写回。

### 第三步

再加回填。

只有确认查询稳定后，再做：

- 备货状态回填
- PCS 回填
- MT 回填

## 5. req3 的推荐实施步骤

### 第一步

先把 `LINE UP` 文件读干净。

也就是：

- 确认船名列
- 确认区域列
- 确认码头信息

### 第二步

做一个查询结果采集器。

只做：

- 输入船名
- 抓查询结果
- 保存原始结果

### 第三步

把“原始结果 -> 九区 / 十区 / 罗泾矩阵”这一步规则固化。

这一步最关键，因为它其实是业务规则，不只是技术规则。

## 6. 这两条需求和 req1 怎么共享一套框架

它们以后完全可以共用：

- 一个统一的 skill 入口
- 一个统一的日志目录
- 一个统一的配置目录
- 一个统一的 Excel 输入输出习惯
- 一个统一的 agent 调度层

## 7. 我建议你后面怎么推进

最好的推进顺序还是：

1. 把 req1 真正用起来
2. 补 req3 的查询和报表
3. 最后再做 req2 的定时回填

因为：

- req1 最容易马上产生价值
- req3 次之
- req2 的网页自动化风险最高
