# 桌面版发布评估与后续方案

这份文档主要回答 5 个问题：

1. 从本地直接用，方不方便
2. 从 GitHub 给别人下载，方不方便
3. 当前完成 req1 / req2 / 预留 req3 的结构顺不顺手
4. 以后继续加功能，维护成本高不高
5. 中文乱码、路径、更新、配置迁移这些坑怎么避

## 一、本地直接使用的评估

### 现在的状态

现在已经有一个给普通用户体验的 release 预览目录：

- `普通用户体验区-桌面应用版-release预览`

普通用户只需要：

1. 打开 `README.html`
2. 双击 `Start AMS Assistant.bat`
3. 通过 GUI 使用 req1 和 req2

### 优点

- 不需要安装 Python
- 不需要研究代码目录
- 工作区固定
- 用户数据固定
- req1 和 req2 都有清晰入口
- 还有 `Run Desktop Self Test.bat` 方便快速自检

### 仍然可能遇到的问题

- 第一次运行时，Windows 可能弹 SmartScreen 提示
- req2 登录层依赖网站本身可用
- req2 登录层依赖 Edge / Chrome / Playwright Chromium 至少一种可用
- 用户如果长时间不关闭 Excel，req1/req2 会因为文件占用而失败

### 当前结论

本地给业务同事试用，已经基本可行。

## 二、从 GitHub 给别人下载的评估

### 当前最不推荐的方式

不推荐让普通用户直接下载 GitHub 源码 ZIP。

原因：

- 源码 ZIP 不是给普通用户看的
- 里面会有脚本、示例、文档、打包目录、历史材料
- 普通用户容易不知道该点哪个文件

### 当前最推荐的方式

推荐在 GitHub 的 Releases 页面放：

- 一个 release 压缩包
- 一个简洁 README
- 一个“从这里开始”的 HTML 说明

普通用户应该下载的是 release 包，而不是源码。

### 当前还缺什么

- 正式 release 命名规范
- release changelog
- 更像产品而不是工程目录的安装体验

## 三、当前结构对 req1 / req2 / req3 是否顺手

### 现在这样拆是合理的

- `maritime-service/`
  负责业务 workflow 和脚本
- `desktop_app/`
  负责 GUI、打包、路径和设置

这是一个比较稳的拆法，因为：

- 业务逻辑和展示层分开
- 以后你想保留脚本模式也行
- 以后你想换 GUI 技术也行

### 对 req3 的好处

req3 现在虽然还没做完，但入口已经预留在 GUI 里了。

以后接 req3 时，只要补这几层：

1. `maritime-service/scripts/` 里加 req3 workflow
2. `runtime.py` 里加 req3 操作桥接
3. `app.py` 里把 req3 页面接活

## 四、以后加新功能方不方便

### 现在的扩展方式

建议继续沿用下面这个模式：

1. 先在 `maritime-service/scripts/` 实现 workflow
2. 用 JSON / Excel / API 明确输入输出
3. 在 `desktop_app/runtime.py` 封装为桌面动作
4. 在 `desktop_app/app.py` 挂到 GUI
5. 再补 release 说明和验收入口

### 为什么这套方式比较稳

- 业务规则不会和 GUI 绞在一起
- 出问题时容易定位是“业务层”还是“界面层”
- 以后可以给同一套 workflow 做网页端、桌面端、命令行端

### 现在最值得保持的约束

- 一个 requirement 尽量对应一个 workflow
- 每个 workflow 都要有固定输入目录和固定结果目录
- 每个 workflow 都要有一套示例
- 每个 workflow 最好都能做自检

## 五、以后改旧功能方不方便

### 目前维护风险最大的地方

1. req2 的网站选择器和接口规则
2. req1 的 Word 模板结构
3. 用户配置字段将来变多后的兼容问题

### 为什么它们风险大

- req2 网站可能改页面、改 token、改字段名
- req1 模板如果版式变化太大，旧替换点可能失效
- 设置文件如果以后加很多项，就需要做配置迁移

### 建议的解决方法

#### 1. 给设置文件加版本号

现在的 `settings.json` 还比较简单，后面建议加：

- `config_version`

这样以后升级字段时，可以写迁移逻辑，而不是靠“有没有这个键”硬猜。

#### 2. req2 要尽量抽出“站点适配层”

后续建议把 req2 再细分成：

- 登录态管理
- 站点请求封装
- 结果字段映射
- Excel 回填

这样以后网站一改，不至于整条链都动。

#### 3. req1 模板逐步从“自由 Word 模板”过渡到“占位符模板”

现在兼容现有模板是对的，但长期看，最好逐步变成更标准的占位符体系。

这样以后新增模板或改模板的人，不需要理解太多代码细节。

## 六、中文乱码与 Windows 兼容问题

### 已经采用的办法

- `.bat` 入口尽量保持 ASCII 内容
- 给普通用户看的主说明改用 HTML
- GUI 内部直接显示中文
- 用户数据路径和工作区路径由程序自动管理

### 以后仍然要警惕的点

- Windows `cmd` 对中文和 UTF-8 的兼容不总是稳定
- Markdown 查看器对编码的判断不一定一致
- 临时脚本里写死中文路径时，PowerShell / Python 管道有时会把字符吃坏

### 目前最稳的建议

- 普通用户说明优先用 HTML
- 批处理内容尽量 ASCII
- 重要文件路径由程序生成，不让用户手敲

## 七、更新策略怎么设计更好

### 当前已经做对的点

- 程序本体和用户数据分开
- 设置文件和工作区不跟程序目录绑死
- GUI 内有检查更新入口

### 下一步最好的方案

#### 阶段 1：release 压缩包 + 手动替换 app

也就是现在这套思路：

- 更新时只替换 `app/`
- 保留 `user-data/`

优点是简单、稳、容易排查。

#### 阶段 2：做一个正式安装器

比如：

- Inno Setup
- NSIS

这会让普通用户体验更像真正的软件：

- 桌面快捷方式
- 开始菜单入口
- 卸载入口
- 更自然的升级体验

#### 阶段 3：再考虑自动更新

自动更新不是不能做，但建议放到后面。

原因很现实：

- 先把 req1 / req2 / req3 做稳更重要
- 自动更新一旦处理不好，反而更容易把用户搞坏

## 八、结论

### 当前结论

这套项目已经从“脚本集合”进入“可发布的桌面工具雏形”阶段了。

### 现在最好的使用方式

- 内部试用：直接使用 release 预览目录
- 对外发布：以后走 GitHub Releases 压缩包
- 后续扩展：继续按 workflow + runtime + GUI 三层往前推

### 现在最值得继续投入的方向

1. 把 req3 接入桌面版
2. 给设置文件做版本迁移准备
3. 继续优化 req2 的站点适配层
4. 以后做正式安装器，而不是长期停留在 bat + 文件夹分发
